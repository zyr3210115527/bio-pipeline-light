## 1. 一句话说清这是什么

**它是一个"生信分析方案的自动规划器"。**

用户用大白话提一个需求，比如：

> "我想看看肝癌病人里哪些基因表达有差异，再做个通路富集。"

系统回给一份**结构化的分析方案**（我们叫它 Plan），里面写清楚：

- 用哪个分析流程（`diff_expr_kegg`）
- 用哪个队列的哪份数据文件（`HRA001272-Genes-TPM-1.0.tsv`，肝癌队列 698 个样本）
- 这份文件在服务器上的真实路径
- 每一步的输入输出格式对不对得上
- 如果数据不够，缺什么，明说

### 一个类比

把它想成**医院的分诊台 + 检查预约系统**：

| 医院 | 本系统 |
|---|---|
| 病人说"我肚子疼" | 用户说"我想做差异表达分析" |
| 分诊台判断该挂哪个科 | 判断该用哪个分析流程 |
| 查这个科今天有没有号、哪台机器空着 | 查图谱里这个队列有没有对应格式的数据文件 |
| 开出一张检查单（科室、时间、注意事项） | 输出一份 Plan JSON |
| **不负责做手术** | **不负责跑分析**——只出方案，执行是下游的事 |

最后一行很重要：**本系统不跑任何生信软件，一个 BAM 文件都不会生成**。它只做"规划"和"数据核对"。

### 为什么这件事不容易

外行会觉得"这不就是个查询系统吗"。难点在三个地方：

1. **意图到工具的映射是模糊的。** "看看哪些基因不一样" 可能指差异表达，也可能指突变景观，也可能指拷贝数变异。用户不会用工具名说话。
2. **数据必须是真实存在的。** 大模型有个致命毛病叫"幻觉"——它会一本正经地编造一个不存在的文件名（比如 `HRA001272_tumor_vs_normal.csv`），格式完全合理，路径看着也像那么回事，但图谱里根本没有。方案交给执行端，跑到一半才炸。
3. **速度。** 每让大模型"思考"一次要几秒到几十秒。规划一次要是来回思考七八轮，用户就等了两分钟。

这三点分别对应了架构里的三块设计：**Skill 手册**（教它怎么映射）、**接地校验**（防幻觉）、**轮数纪律**（控速度）。

## 2. 背景：原来是怎么做的，为什么要重做

### 2.1 原版（重架构）

原来有个项目叫 **bio-pipeline-kg-matcher**（下文简称"重版"）。它是一个 **205 MB** 的服务，里面塞了：

- 一个内嵌的大模型调用（超时设到 180 秒，输出上限 16k）
- 两套数据匹配器（一套读 CSV，一套读图数据库，互相对比）
- 113 个 CSV 文件
- 157 个审计文件
- 16 个演示录像（cassettes）
- 一个 132 KB 的 `workflow_composer.py`，里面是成千上万行 if-else 规则

用户提一个需求，调它的 `route_pipeline_request` 接口，它**一次调用就返回一份现成的 Plan**。

听起来很方便。问题在于：

**问题一：推理逻辑被硬编码进了服务里。**
"用户说了'差异'就选 diff_expr" 这类规则写死在代码中。新增一个分析流程要改代码、重新部署。而且规则本身是脆的——用户不说"差异"改说"哪些基因在两组之间不一样"，规则就不认了。

**问题二：206 MB 的体积里，绝大部分是死重量。**
113 个 CSV、157 个审计文件、16 个录像，对"规划一次分析"这件事没有任何贡献，只是历史沉淀。

**问题三——这条最要命：我们后来发现，原版一直在拿一个"泄题的考卷"给自己打分。**

详见第 9 章。简单说：那套 96 道题的测试集里，**96 道题的题面都直接包含了答案的触发词**。比如题目问"请做 WGCNA 共表达网络分析"，答案就是 `wgcna` 这个工具。这种题，用一张 60 行的关键词对照表就能考 100 分——根本不需要 AI，也根本证明不了那 205 MB 有任何价值。

### 2.2 轻架构的主张

于是有了 **bio-pipeline-light**（下文简称"light"）。核心主张一句话：

> **推理交给调用方的大模型，服务端只提供知识和确定性校验。**

拆开说：

- **服务端不做推理。** 不再有"一次调用出 Plan"的接口。服务端只回答"图里有什么"和"你这份方案对不对"。
- **推理写成一份手册**（Skill），交给大模型自己读、自己想。手册是纯文本，改一行就生效，不用改代码、不用重新部署。
- **凡是能确定性算出来的，不让模型算。** 工具在不在闭集里、文件在不在图里、路径是不是真的——这些用代码查一遍就知道，绝不能让模型"觉得"。

体积从 **205 MB 降到约 110 KB**（skill 手册 + 一个 Cypher 查询通道），差了三个数量级。

## 3. 架构总览：四层结构

```
┌─────────────────────────────────────────────────────────────────┐
│  第四层  编排层                                                   │
│  web/server.py（纯 Python 标准库，零第三方依赖）                    │
│  · 拼系统提示词（手册全文内联进去）                                  │
│  · 跑 function-calling 循环（模型想调工具 → 转发给 MCP → 回结果）    │
│  · 终答后自动补全 + 自动接地校验（模型看不见这两步）                  │
│  · SSE 推流给前端（思考段、工具调用可视化）                          │
└───────────────┬─────────────────────────────────┬───────────────┘
                │                                 │
        ┌───────▼────────┐              ┌─────────▼──────────┐
        │  第二层  Skill  │              │  第三层  MCP 工具    │
        │  SKILL.md      │              │ mcp_light_server.py │
        │  (英文全量,     │              │  10 个工具           │
        │   709 行)      │              │  · 查图              │
        │  manual_compact│              │  · 队列画像          │
        │  .md           │              │  · 角色判定          │
        │  (中文精简,     │              │  · 闭集校验          │
        │   369 行)      │              │  · 接地校验          │
        │                │              │  · 确定性补全        │
        │  = 写给 AI 的   │              │                     │
        │    作业手册     │              │ = AI 的手和眼睛      │
        └────────────────┘              └─────────┬──────────┘
                                                  │ 只读 Cypher
                                        ┌─────────▼──────────┐
                                        │  第一层  知识图谱    │
                                        │  Neo4j              │
                                        │  81,628 节点         │
                                        │  364,184 关系        │
                                        │                     │
                                        │ = 唯一的事实来源     │
                                        └────────────────────┘
```

**一句话概括每一层的职责：**

| 层 | 是什么 | 职责 | 关键约束 |
|---|---|---|---|
| 知识图谱 | 一个 Neo4j 数据库 | 记录"有哪些工具、哪些数据、怎么串" | **唯一事实来源**，只读 |
| Skill | 两份 Markdown 文档 | 教大模型怎么规划 | 纯文本，改完立即生效 |
| MCP 工具 | 一个 Python 进程 | 给大模型提供查询和校验能力 | 不做推理，只做确定的事 |
| 编排层 | 一个 HTTP 服务 | 把上面三层和大模型串起来 | 纯标准库，无依赖 |

### 3.1 什么是 MCP？

**MCP = Model Context Protocol（模型上下文协议）**，是 Anthropic 提出的一个开放标准，用来规定"大模型怎么调用外部工具"。

打个比方：USB 之前，每个鼠标键盘打印机都有自己的接口。USB 出来之后，只要符合 USB 标准，插上就能用。MCP 之于 AI 工具就是这个作用——只要你的服务按 MCP 标准暴露工具，任何支持 MCP 的 AI 客户端（Claude Code、Cursor、我们自己的网页前端）插上就能用。

我们的 `mcp_light_server.py` 就是这样一个"USB 设备"：它对外声明"我有 10 个工具，每个叫什么、要什么参数、返回什么"，剩下的由客户端和模型自己去用。

### 3.2 什么是 Skill？

Skill 是一份**写给 AI 看的操作手册**。它不是代码，不会被"执行"——它是被**读进模型的上下文**里，作为模型的行动指南。

关键区别在这：

| | 代码里的规则 | Skill 手册 |
|---|---|---|
| 谁执行 | CPU 机械执行 | 大模型理解后自行判断 |
| 遇到没写到的情况 | 直接失败 / 走 else 分支 | 模型按手册的**精神**外推 |
| 改一条规则 | 改代码、测试、重新部署 | 改一行文字，重启即可 |
| 能不能"举一反三" | 不能 | 能 |

**重要：Skill 是写给 AI 的，不是写给人的。** 这一点直接决定了它的文风——第 5 章会展开。

## 4. 第一层：知识图谱（数据从哪来）

### 4.1 什么是知识图谱

普通数据库（Excel、MySQL）用**表格**存数据：一行一条记录，一列一个字段。
知识图谱用**点和线**存数据：**节点**（Node）是实体，**关系**（Relationship）是实体之间的连线。

举例。表格要表达"STAR 这个工具的下游是 featureCounts"，得建一张"工具关系表"，两列都是外键，查的时候要 JOIN。图谱里直接就是：

```
(STAR) ──next_tool──> (featureCounts)
```

好处是**多跳查询极快且直观**。比如问"从 FASTQ 原始数据出发，能走到哪些最终产物"，在图里就是从一个节点沿着 `next_tool` 边一路走下去，一句 Cypher 搞定；在表格里要写好几层嵌套 JOIN。

**Cypher** 是 Neo4j 的查询语言，相当于图数据库的 SQL。长这样：

```cypher
MATCH (t:tool)-[:next_tool]->(next:tool)
WHERE t.tool_name = 'star'
RETURN next.tool_name
```

读作："找到所有叫 star 的 tool 节点，沿 next_tool 边走一步，把走到的节点名字返回来。"

### 4.2 我们这张图里有什么

规模（0821 交付版本）：**81,628 个节点，364,184 条关系**。

**节点类型（左边是类型名，括号里是数量）：**

| 节点类型 | 数量 | 存的是什么 |
|---|---|---|
| `tool` | 51 | 分析工具/流程。每个带中文功能描述、输入输出格式 |
| `function` | 90 | 分析功能（中文句子），如"差异表达分析" |
| `format` | 42 | 数据格式，如 `RAW_PAIRED_END_R1_FASTQ`、`MUTATION_ANNOTATION_FORMAT_MAF` |
| `modal` | 6 | 组学模态：WES / WGS / bulk_RNA / sc-RNA / Clinical / Meta |
| `datalevel` | 4 | 数据层级：1 原始 → 4 知识 |
| `study` | 20 | 研究队列，如 HRA001272（肝癌，698 样本） |
| `project` | 18 | 项目 |
| `individual` | 7,131 | 病人个体 |
| `sample` | 10,465 | 样本 |
| `T1` | 28,229 | **原始数据文件**（FASTQ 等） |
| `T2` | 35,572 | **加工产物文件**（BAM / VCF / MAF / 表达矩阵等） |

**关系类型（举主要的）：**

| 关系 | 含义 |
|---|---|
| `(tool)-[:next_tool]->(tool)` | 工具链接续：A 的产物能喂给 B |
| `(tool)-[:input\|output]->(format)` | 工具的输入/输出格式契约 |
| `(tool)-[:suitable_for]->(modal)` | 这个工具适用于哪种组学 |
| `(tool)-[:has_function]->(function)` | 这个工具能做什么分析 |
| `(T1\|T2)-[:in_sample]->(sample)` | 文件属于哪个样本 |
| `(T2)-[:generated_from]->(T1)` | 加工产物是从哪个原始文件来的 |
| `(sample)-[:in_individual]->(individual)` | 样本取自哪个病人 |
| `(individual)-[:in_study]->(study)` | 病人属于哪个队列 |

### 4.3 三个必须讲清楚的"坑"

这三条在讲课时值得单独讲，因为它们体现了"为什么手册里要写那么多实测细节"。

**坑一：T1 里没有 BAM。**
直觉上"原始数据表"应该什么都有。实际上 **T1 只有 FASTQ**（`RAW_PAIRED_END_R1_FASTQ`/`R2` 各 14,092 个），外加每个队列一份临床表和一份样本元信息表。**所有的 BAM、VCF、MAF、表达矩阵都在 T2。**
如果模型写了 `MATCH (t:T1) WHERE ... 'BAM'`，返回零行——**不是数据没有，是查错了表**。手册里必须写死这条，否则模型会把零行读成"该队列没有数据"，然后报 `no_candidate`。

**坑二：`format` 是小写扩展名，`semantic_format` 才是语义名。**
T2 上有两个看起来都像"格式"的字段：

- `format` = `bam` / `vcf.gz` / `maf`（小写文件扩展名）
- `semantic_format` = `DNA_ALIGNMENT_BQSR_BAM` / `MUTATION_ANNOTATION_FORMAT_MAF`（大写语义名）

写 `WHERE t.format CONTAINS 'BAM'` 永远匹配不到——大小写不对。这类错误不报错，**只是安静地返回零行**，是最难查的一种 bug。

**坑三：数据本身有脏字段，而且脏得"看着像对的"。**
0821 那版交付把**样本级事实覆盖成了队列级默认值**。举个具体的：

- `tumor_descriptor` 字段本来该区分"原发/转移/复发"。实际上全图只剩 `Primary` 8,551 个、`Metastasis` 12 个——原来的 210 个 `Metastatic` 和 407 个 `Recurrent` 被压平成了 `Primary`。**更糟的是 1,470 个 `tissue_type='Normal'` 的样本也被标成了 `Primary`**（一管正常血被标成"原发肿瘤"，自相矛盾）。
- `biospecimen_anatomic_site` 字段本该是样本的取材部位。实际上 HRA001272 全部 698 个样本都写着 `Liver And Intrahepatic Bile Ducts`，尽管这些样本的名字里明明写着十种不同的转移部位（肺转移、腹膜转移、骨转移……）。

**这些坏值不是空的，也不是格式错的——每一格都填得满满当当，每个值单看都合理。** 所以查询会开开心心返回一堆行，只是选中了错的样本。

这就是为什么手册第 12 章要专门列一节"**不可信字段黑名单**"：不是给人看的注释，是**直接禁止模型在这些字段上做筛选**。

## 5. 第二层：Skill（写给 AI 看的作业手册）

### 5.1 两份文件，派生关系

| 文件 | 语言 | 规模 | 谁在读 |
|---|---|---|---|
| `skill/SKILL.md` | 英文全量 | 709 行 / 73 KB | 外部 MCP 客户端（通过 `get_planning_guide` 取） |
| `web/manual_compact.md` | 中文精简 | 369 行 / 37 KB | **我们自己的网页服务**（启动时内联进系统提示词） |

**这两份是派生关系：改了一份必须同步另一份。** 内容一一对应，只是详略和语言不同。

为什么要两份？因为用途不同：

- 外部客户端（比如别人用 Claude Code 接我们的 MCP）需要一份**自包含、可以单独分发**的英文手册。
- 我们自己的网页服务把手册**直接塞进系统提示词**——每次对话开头模型就已经读到了，省掉"先调 `get_planning_guide` 取手册"这一整轮往返（一轮就是几秒到几十秒）。既然是塞进提示词，就要尽可能短，所以做了中文精简版。

### 5.2 手册里有什么（12 节）

| 节 | 标题 | 作用 | 为什么需要 |
|---|---|---|---|
| §1 | Tools (9) | 十个工具各自什么时候调 | 模型不知道该用哪个工具时的速查表 |
| §2 | 图谱模型 | 每种节点有哪些属性、哪些属性有坑 | 不写清楚模型就得先查一遍 schema，浪费一轮 |
| §3 | 闭集工具目录 | 51 个工具的完整清单 + 组装规则 | **闭集**是硬约束：不在这 51 个里的工具一律不许出现在答案里 |
| §4 | 查询配方 | 15 条官方 Cypher 模板 + 标准查法 | 让模型抄现成的，别自己现编 Cypher |
| §5 | 规划五步法 | 解析需求 → 匹配工具 → 组链 → 选数据 → 出 Plan | 固定流程，避免模型东一榔头西一棒 |
| §6 | **效率纪律** | 轮数预算、并行发查询、什么时候必须停 | **这一节直接决定响应速度**，见 5.4 |
| §7 | 接地纪律 | 答案里每个名词都必须来自手册或查询结果 | **防幻觉的核心**，见 5.5 |
| §8 | 拒绝纪律 | 无关问题 / 隐私问题怎么回 | 合规 + 省算力 |
| §9 | 输出契约 | tool-chain/v2 JSON 的字段定义 | 下游按这个格式解析，格式错就等于失败 |
| §10 | 提交前把关 | 要真的跑分析时怎么校验参数 | 只在"要提交执行"的场景用 |
| §11 | 边界与原则 | 隐私红线、能说什么不能说什么 | |
| §12 | **实测快照** | 队列样本数表、T2 产物清单、脏字段黑名单 | **让模型不用查就知道**，见 5.3 |

### 5.3 §12 实测快照：用空间换时间

这是整份手册里**篇幅最大**的一节，也是最反直觉的设计。

它把一些**本来可以查数据库得到的事实，直接写进了手册**。比如：

```
| study_accession | tumor_type | sample nodes |
|---|---|---|
| HRA001272 | hepatocellular carcinoma | 698 |
| HRA000074 | malignant glioma | 693 |
| HRA016026 | lung cancer | 700 |
...（20 个队列全列）
```

以及 T2 产物清单：

```
| T2 semantic_format | count | 分布在哪些队列 |
|---|---|---|
| DNA_VARIANT_VCF_GENERAL | 8310 | HRA000873(3045), HRA001272(1909), ... |
| MUTATION_ANNOTATION_FORMAT_MAF | 2355 | 只有七个队列有 |
| SCRNA_MATRIX_H5 | 403 | HRA005191(243), HRA001748(160) |
```

**为什么要这么干？** 因为查一次数据库对**服务端**来说不到 0.5 秒，但它意味着模型必须**多想一轮**——而模型想一轮要几秒到几十秒。

把"肝癌队列是 HRA001272，有 698 个样本"这种**几乎每次都要用、又极少变**的事实直接写进手册，模型开口就能用，一轮都不用花。

代价：**图谱数据换版本时，这一节必须重新逐条查出来改掉**，否则模型会拿旧数字规划。这个代价我们认，并且写进了 README。

### 5.4 §6 效率纪律：为什么这一节最值钱

先讲清楚一个成本结构，这是整个优化工作的基础：

| 动作 | 耗时 | 说明 |
|---|---|---|
| 模型思考一轮 | **几秒 ~ 几十秒** | 一轮 = 一次完整的模型推理 |
| 执行一条 Cypher 查询 | **< 0.5 秒** | 几乎免费 |

**结论：轮数是唯一的成本，查询次数几乎不要钱。**

于是手册里立了这些规矩：

**规矩一：清单式开火（最重要的一条）**
每轮开始前，先把"我还需要知道什么"全列出来，然后把**所有参数已知的查询在同一轮里全部发出去**。

> 6 条查询分 6 轮发，比分 3 轮发慢一倍。

典型的可并行组合（手册里直接给出）：
- "按功能找工具" + "按癌种找队列" —— 互不依赖，第一轮一起发
- "查该队列的现成矩阵" + "判定该队列样本角色" —— 都只依赖队列号，一起发

只有**真正的串行依赖**（必须先拿到队列号才能查它的文件）才允许分轮。

**规矩二：标准轨迹三轮**
```
R1: 从 §12 快照里选工具和队列（不查询！）
    → 同一轮发出 get_study_overview + 一个 read_cypher_batch + 需要的话 validate_atomic_chain
R2: 用 R1 的证据组装 Plan
R3: 输出最终 JSON
```
拒绝类问题（无关提问、隐私提问）：**1 轮，零工具调用**。

**规矩三：查过就别再查**
同一个工具契约、同一个队列，最多查一次，后面引用前面的结果。

**规矩四：该停就停**
查询返回空 → 先检查关键词语言（中文还是英文）和目标表（T1 还是 T2），**不许把同一条失败查询再发一遍**。硬上限 6 轮；到顶还分不出同族工具，就选证据最强的那个，在 `match_note` 里说明歧义，然后出答案——**不许继续查**。

这条纪律的效果，第 9 章有数字。

### 5.5 §7 接地纪律：防幻觉

**"接地"（grounding）** = 答案里的每一个具体名词，都必须能追溯到一个真实来源。

手册里的规定：

1. **名词白名单。** 答案/Plan 里出现的每一个工具名、队列号（HRA*）、文件名、路径、格式名、样本号，**必须逐字来自**这份手册或本次会话的工具返回结果。拿不准某个名词是不是真见过 → 重新查一遍确认，或者干脆不用。

2. **不许用内部知识补全。** 图里没有的工具/数据/链路环节 → 老老实实输出 `missing_from_graph` / `no_candidate` / `unsupported`。
   > 哪怕你"知道" DESeq2、Seurat 确实存在——只要不在这 51 个闭集工具里，就不许出现在答案里。

3. **证据可追溯。** `match_note`（推荐理由）必须对应到某条真实查询结果；样本角色只能来自 `resolve_sample_roles` 工具；路径只能来自图谱记录。

4. **输出前自检。** 成品 Plan 先过 `hydrate_plan`（补全），再交给 `validate_plan`（接地校验）。返回 `grounded=false` 就按 `violations` 清单修，**用已经查到的证据修，不许重新开始探索**。

**这一层为什么必须有：** 大模型编造内容时的置信度和说真话时**完全一样**。它不会说"我不确定"，它会给你一个格式完美、命名规范、路径合理的**假文件名**。人眼几乎分辨不出来。唯一可靠的办法就是**拿去和图谱逐条比对**——这是代码能做的确定性工作，不该让模型"努力不要编"。

### 5.6 这次做的精简：为什么删的是"叙述"

用户要求"精简 skill，去掉多余的叙述——skill 是写给 AI 的，有的不必要人类能完全理解"。

这个判断是对的，而且落到具体条目上很清晰。手册里存在两类文字：

| 类型 | 例子 | 处理 |
|---|---|---|
| **操作性规则** | "T2 的 `format` 是小写扩展名，查语义要用 `semantic_format`" | **一个字不能删** |
| **说服性叙述** | "实测 29 个多轮例子里 13 个栽在这：先在 T2 按 format 猜、查空了再去 T1 按 strategy 猜" | 删掉论据，保留结论 |

后一类是**写给人看的**——它在向读者证明"这条规则不是我拍脑袋定的"。但模型不需要被说服，它需要被告知。

具体删了这些：

- 96 例实测的分项统计（"29 个里 13 个"）→ 保留结论"**这是本项目最大的时间浪费**"
- 0821 那次观察到"低思考预算的模型连调 7-10 次 validate_plan"→ 删，保留"**最多调 2 次**"这条硬预算
- pre-0821 图谱的孤儿文件数（3,758 runs / 7,516 T1）→ 删，保留"**不要拿旧结论否掉队列**"
- 某个案例"为了一个字段推理 4 万字、撞满 token 上限、交了空答案"→ 删，保留"**填不出就置 null，绝不为一个字段多查一轮**"
- 队列默认选择那一大段散文（胶质瘤/肝癌/黑色素瘤各走哪个队列）→ **改成表格**，事实一条没少，篇幅减半

同时保留了所有：实测数字（队列样本数、文件计数）、队列号、字段名、每一条禁令。

**核对方式：** 把新旧两版里出现的所有标识符（HRA*/HRR*/文件名/反引号字段名）和所有 3 位以上的数字提取成集合做差集，确认丢掉的**全部**是被删叙述里的数字（如那个 200 秒、3,758、7,516），没有一个操作性事实被误删。

结果：SKILL.md 726 → 709 行（75.4 KB → 73.3 KB），manual_compact.md 内容同步。剩下的 73 KB 里绝大部分是**数据表**（51 个工具的中文描述、20 个队列快照、T2 产物清单）——那是操作性内容，不是叙述，不能删。

## 6. 第三层：MCP 工具（AI 的十件工具）

十个工具分四类：

| 类别 | 工具 | 作用 |
|---|---|---|
| **取手册** | `get_planning_guide` | 拿到作业手册 |
| **查数据** | `read_cypher` / `read_cypher_batch` / `get_study_overview` / `resolve_sample_roles` | 从图谱取事实 |
| **做校验** | `validate_atomic_chain` / `validate_execution_chain` / `validate_plan` | 确定性检查 |
| **补全 & 运维** | `hydrate_plan` / `health_check` | 填样板字段 / 体检 |

下面逐个讲。每个都给：**干什么 → 怎么调 → 返回什么 → 什么时候用 → 为什么要有它**。

---

### 6.1 `get_planning_guide()` — 取手册

**干什么：** 返回 `SKILL.md` 全文。

**怎么调：**
```json
{"name": "get_planning_guide", "arguments": {}}
```
无参数。

**返回：** 手册全文（约 73 KB 文本）。

**什么时候用：** 会话开始时调一次。

**⚠️ 一个容易搞错的点：** 我们自己的网页服务**从不调它**——手册已经内联进系统提示词了，再调一次纯属浪费一轮。但**服务端必须保留这个工具**，因为其他客户端（Claude Code、别人的 agent）就是靠它拿手册的。

> 讲课要点：这是"同一个服务，不同客户端用法不同"的典型例子。网页端为了省一轮做了内联优化，但不能因为自己不用就把接口删了。

---

### 6.2 `read_cypher(query)` — 只读查图

**干什么：** 对 Neo4j 执行一条只读 Cypher 查询。这是最基础、最通用的取数通道。

**怎么调：**
```json
{"name": "read_cypher", "arguments": {
  "query": "MATCH (s:study) WHERE toLower(s.tumor_type) CONTAINS 'liver' RETURN s.study_accession, s.sample_count"
}}
```

**返回：** 查询结果的行数组。超过 500 行时截断，并带上 `truncated: true` 和 `row_count`。

**三重守卫（这是重点）：**

1. **拒绝写入。** 任何 `CREATE` / `MERGE` / `DELETE` / `SET` / `LOAD CSV` 一律拒绝。图谱是只读的咨询面。
2. **隐私守卫。** `individual` 节点上所有 `01_` 到 `13_` 编号前缀的属性都是**患者级敏感数据**：
   - `01_` 人口学（年龄、性别、种族）
   - `02_` 家族史 · `03_` 生活史（吸烟等） · `04_` 血液学
   - `09_` 肿瘤病理分期 · `10_` 侵犯 · `11_` 分子指标（TMB、MSI）
   - `12_` 治疗史 · `13_` **生存数据**

   这些属性**只允许聚合统计**（`count`、`avg`）或**存在性判断**（`IS NOT NULL`），**不允许取个体值**。只有 `00_*` 开头的操作性标识（样本号、run 号、平台）放行。
   守卫还防了三种绕过手法：整节点导出、`properties()` 函数、动态下标取值。
3. **自动限流。** 查询没写 `LIMIT` 就自动加 `LIMIT 500`。

> **为什么隐私守卫按数字前缀判、而不是按字段名判？** 因为上游随时可能加新的编号列。按名字判（"看着像临床字段就拦"）会漏掉新增的；按前缀判，新增的 `05_xxx` 自动就被拦住了。这是"**用结构判定，不用启发式判定**"的一个例子——这个思路在项目里出现了好几次。

**为什么要有它：** 这是整个"轻架构"主张的支点。原版有一堆专用查询接口（`query_data_availability` 等），light 用**一个通用只读通道 + 15 条官方模板**就 1:1 替代了。新增查询需求不用改服务端代码。

---

### 6.3 `read_cypher_batch(queries)` — 批量查图

**干什么：** 一次调用执行多条**相互独立**的查询，结果按顺序返回。

**怎么调：**
```json
{"name": "read_cypher_batch", "arguments": {
  "queries": [
    "MATCH (t:tool)-[:has_function]->(f:function) WHERE f.name CONTAINS '差异' RETURN t.tool_name",
    "MATCH (s:study) WHERE toLower(s.tumor_type) CONTAINS 'liver' RETURN s.study_accession"
  ]
}}
```
单次最多 8 条。每条与 `read_cypher` 同等守卫。

**返回：** `results[]`，按输入顺序对应。

**什么时候用：** **凡是不依赖上一条返回值的查询，都必须打包进一次 batch。**

**为什么要有它——这是速度优化的关键一环：**

假设模型要问 3 个互不相干的问题。

- 用 `read_cypher` 分 3 轮问：3 × 模型思考时间 ≈ 十几秒到几十秒
- 用 `read_cypher_batch` 一次问完：1 × 模型思考时间 + 3 × 0.5 秒 ≈ 几秒

**功能完全一样，时间差好几倍。** 这就是为什么手册 §6 把"清单式开火"列为第一条纪律，也是为什么这个工具在描述里就写着"不要在多轮里逐条发"——工具描述本身也是给模型看的提示。

---

### 6.4 `get_study_overview(study)` — 队列画像一包到底

**干什么：** 给一个队列号，一次性返回关于这个队列你想知道的一切。

**怎么调：**
```json
{"name": "get_study_overview", "arguments": {"study": "HRA001272"}}
```

**返回（一包全给）：**
- study 基本信息（癌种、标题、描述、个体数）
- sample 节点数（真实样本数，不是 `sample_count` 属性——那个有 6 个队列是空的）
- T1 的格式/策略分布
- T2 的格式/策略分布 + 现成文件样例
- 样本角色分布（`sample_roles`）、角色能否判定（`role_resolved`）
- 文件覆盖度（`file_coverage`）

**什么时候用：** **选定队列之后立刻调**，一次拿齐"这个队列有什么数据、能不能做配对分析"。

**为什么要有它：** 它是一个**为了省轮数而做的聚合接口**。

在它出现之前，模型选定队列后要连着问三件事：
1. 这个队列什么情况？（`read_cypher` 查 study）
2. 它有哪些文件？（`read_cypher` 查 T1/T2）
3. 它的样本能不能分肿瘤/正常？（`resolve_sample_roles`）

这三件事**参数完全相同**（都只需要队列号），完全没有互相依赖，但如果模型一条条问，就是 3 轮。

`get_study_overview` 把它们焊成一个工具——**模型连"我要并行发"这个判断都不用做**，调一次就够了。

> 讲课要点：这是接口设计的一个通用思路——**当发现使用者总是把 A、B、C 三个调用连在一起用，就把它们合成一个新接口**。省的不是服务端的计算，是使用者的决策成本和往返延迟。

---

### 6.5 `resolve_sample_roles(study | records)` — 确定性判样本角色

**干什么：** 判定样本是**肿瘤（tumor）**还是**正常对照（normal）**。规则从重版移植过来，**是确定性代码，不是模型猜的**。

**两种模式：**

模式一，队列模式——看整个队列的角色分布：
```json
{"name": "resolve_sample_roles", "arguments": {"study": "HRA016026"}}
```
返回 `sample_roles`（角色统计，覆盖全部样本）、`role_resolved`（这个队列的角色到底判不判得出来）、`file_coverage`（文件侧覆盖度）。
注意：`samples` 明细默认只回 20 条预览，超出会带 `samples_truncated` —— **统计要看 `sample_roles`，不要数 `samples` 数组**。

模式二，记录模式——对给定的样本逐条判：
```json
{"name": "resolve_sample_roles", "arguments": {"records": [
  {"sample_accession": "HRS123456", "tissue_type": "Tumor", "sample_name": "L0012_Tumor"}
]}}
```

**什么时候用：** **做配对/分组分析、选数据之前必须调。**（配对 WES、原子链需要逐样本挑文件时）
反过来，**选队列级的矩阵或 MAF 不需要调它**——那些流程自带分组逻辑。

**为什么要有它——这是"不许模型猜"的典型：**

判肿瘤还是正常，听起来是件很简单的事：看 `tissue_type` 字段是 `Tumor` 还是 `Normal` 不就行了？

实际数据长这样（0821 实测，全图 10,465 个样本）：

```
Tumor 6258 | Normal 2821 | null 829 | Blood 557
```

- 有 **829 个样本这个字段是空的**
- 有 **557 个写的是 `Blood`**（血样，既不是 `Tumor` 也不是 `Normal` 的字面值）
- 另一个字段 `specimen_type` 还有 **486 个分号多值**（`Organoid;Patient_Solid_Tissue`）
- 更早的交付里 `tissue_type` 甚至有 700 个 `Tumor,Normal` 多值单元，0821 清掉了——**但手册里那条记录一直没更新，直到这次写文档时才发现**（见下）

如果让模型自己看着办，它会：对着 `= 'Tumor'` 做等值匹配，然后**安静地漏掉那 1,386 个 null 和 Blood 样本**——查询不报错，只是结果少了一大块。

所以这条规则被写成了代码，做成工具。手册里配套写死了一条：**"样本角色只能来自 `resolve_sample_roles`，永远不许从文件名或直觉推断。"**

**配套的两张实测表**（直接写进了手册 §4，模型不用查）：

- **能做同个体配对的队列**（0821 实测个体数）：HRA000873 1015、HRA000021 508、HRA016026 350、HRA001272 206、HRA003107 155、HRA001749 84、HRA007169 76、HRA006499 72
  - 陷阱：**HRA000071 的血液对照和肿瘤样本不属于同一个体**——能做分组，不能做同个体配对
  - 要现成配对优先 HRA016026（350 个体各 2 样本，`L####_Tumor`/`L####_Normal`，350/350 全配上）
- **角色判不出来的队列**（别浪费轮数重试）：HRA000001（557 个全是 Blood）、HRA000074（693 里 543 个没 `tissue_type`）、HRA005191、HRA002693、HRA006117、HRA000122
  - **关键补充：这只卡"逐样本配对"这一件事。** 这些队列的队列级分析（差异表达、富集、聚类、免疫浸润、生存）照常能做——那些流程用的是汇总矩阵/MAF，自己内部分组。**不许因为角色判不出来就报 `no_candidate`。**

### 6.6 `validate_atomic_chain(chain)` — 原子链闭集校验

**先解释两个词：**

- **atomic tool（原子工具）**：单个生信软件，比如 `bwa`（比对）、`gatk`（变异检测）、`star`（RNA 比对）。它们可以**串成链**：`trim_galore` → `star` → `featurecounts`。
- **pipeline（业务流程）**：一个打包好的完整分析，比如 `diff_expr_go`（差异表达 + GO 富集）。它内部可能包含多个步骤，但对外是一个整体，**不参与串链**。

**闭集**的意思是：可编排的原子工具**只有 11 个**，多一个都不行。

**干什么：** 给一条原子工具链，校验两件事：
1. 每个工具都在那 11 个闭集成员里
2. 相邻两步在图谱里真的有 `next_tool` 边（不是你以为能接就能接）

**怎么调：**
```json
{"name": "validate_atomic_chain", "arguments": {
  "chain": ["trim_galore", "star", "featurecounts"]
}}
```
参数是有序的工具 id 数组。

**返回：** 校验结果 + 规范化的 `tool_chain`——**这里有个附加价值**：返回的链用的是 **Knowledge Card 的 `meta.id`** 和卡内定义的输入输出名。比如你传 `star`，回来的是 `star_rrna_and_genome_alignment`，还告诉你它的输入槽叫 `read1`/`read2`。

**什么时候用：** 链组装完之后调**一次**。不要边探索边调。

**为什么要有它：** 这是整个架构里"**确定性校验不可替代**"的证据。

README 里有一句诚实的话：原版的 `validate_tool_chain` 在 light 里是"规则近似"——因为**要做到 96 例评测级的严格保证，就必须有真正的闭集校验代码**，不能靠模型判断。这个工具就是那几百行代码。

模型可以搞错"samtools 之后能不能直接接 snpEff"，但代码查一下图里有没有那条边，是不会错的。

---

### 6.7 `validate_execution_chain(steps)` — 提交前把关（最复杂的一个）

**干什么：** 用户/前端要真的把这条链投给执行端去跑之前，做**五阶段体检**，并算出**可以直接下发的执行参数**。

**五个阶段：**
1. **注册校验** —— 这些工具存在吗？
2. **卡契约必填输入** —— 每张 Knowledge Card 声明的必填输入都给了吗？
3. **绑定结构** —— 给的绑定格式对吗？
4. **数据探查** —— 绑的文件在图里真的有确认路径吗？
5. **链流转** —— 上一步的产物能喂给下一步吗？

**怎么调：**
```json
{"name": "validate_execution_chain", "arguments": {
  "steps": [
    {"tool_id": "trim_galore",
     "inputs": {"read1": {"file_name": "a_R1.fq.gz", "file_path": "/data/a_R1.fq.gz"},
                "read2": {"file_name": "a_R2.fq.gz", "file_path": "/data/a_R2.fq.gz"}}},
    {"tool_id": "star",
     "inputs": {"read1": {"file_name": "a_R1_val_1.fq.gz", "file_path": "/data/a_R1_val_1.fq.gz"},
                "read2": {"file_name": "a_R2_val_2.fq.gz", "file_path": "/data/a_R2_val_2.fq.gz"}}}
  ]
}}
```

**返回（`tool-chain-validation/v1.2` 契约）：**

| 字段 | 含义 |
|---|---|
| `validation` | 五阶段逐段报告，含 `errors` |
| `execution_params` | **扁平便捷视图**：`{参数名: 真实路径}`。键是 **Knowledge Card 的参数名** |
| `execution_params_by_step` | **多步链以此为准**：`[{step, tool_id, params}]` |
| `execution_params_ambiguous` | 跨步同名冲突的参数（见下） |
| `execution_params_missing` | 缺什么，元素是对象 `{param, tool_id, step, reason}` |
| `submittable` | **能不能提交**（布尔） |

**判定标准：`errors` 清零**且** `submittable=true` 才可以提交。**

**四个必须讲清楚的细节**（这些是我们在 0823 那轮专门修的）：

**① `Array[File]` 参数的值是数组，不是字符串。**
`fastqc` 的 `fastqs`、`multiqc` 的 `qc_files` 类型是 `Array[File]+`（WDL 的非空数组）。它们在 `execution_params` 里的值是**路径数组**。消费方不能假设值一定是字符串。

**② 参考资源既不映射、也不报缺。**
有 5 个 File 类型的参数是**带卡片默认值的参考/索引资源**——执行端容器里已经有了，用户不用给：
`star` 的 `rrna_star_index` 和 `genome_star_index`、`rsem` 的 `rsem_index`、`featurecounts` 的 `gtf_file`、`gatk` 的 `interval_list`。

**这里有个非常值得讲的坑：** 判定"是不是参考资源"**必须用显式白名单，绝不能用关键词猜**。

看这一条：
```
bcftools_somatic_postprocess   filtered_vcf_index   File   TBI   required=true
```
它的名字里带 `index`。但它**不是**参考资源——它是数据文件的伴随索引（`.tbi`），没有默认值，缺了 bcftools 直接跑不起来。

重版就是踩了这个坑：按 "index" 关键词把它判成参考资源，于是**既不映射也不报缺**，一条必需的绑定就这么静悄悄消失了，0823 才修掉。

所以 light 这边写成了一张 **`(卡片 id, 参数名)` 二元组的显式白名单，正好 5 条**，新工具接入时手动加。

> 讲课要点：**"看起来像"不等于"是"。** 关键词启发式在小样本上总是好用，在真实目录里总会撞上反例。凡是能列举的，就别猜。

**③ 多步链要看 `execution_params_by_step`，扁平视图会剔除冲突。**
`trim_galore` 和 `star` 都有一个叫 `read1` 的参数。但它们指向**不同的文件**（`star` 吃的是 `trim_galore` 处理过的产物）。

扁平的 `execution_params` 是个字典，一个键只能有一个值。怎么办？

我们的处理是：**冲突的键从扁平视图里剔除**，放进 `execution_params_ambiguous`，逐步的值在 `by_step` 里完整保留。

> **宁可缺，不给静默覆盖的错路径。**

手册里配套写明："扁平视图里没有的参数不等于缺，去 `by_step` 里取。"

**④ 回包里的 `tool_id` 是卡片的 `meta.id`，不是你传进去的图谱 id。**
你传 `star`，`by_step` 里回来的是 `star_rrna_and_genome_alignment`。这和 `normalized_steps` 的约定一致。没有卡片的 pipeline 级工具则原样回传。

**所以对步骤请按 `step` 下标取，不要拿 `tool_id` 字符串去匹配你的请求。**

**为什么这个工具存在——一个"错得像对"的故事：**

这个工具在 0823 之前有个严重问题。给它一条**完全正确**的 `fastqc` 单步链，它返回：

```
errors          : []          ← 没错误
execution_params: {}          ← 空的
params_missing  : []          ← 也是空的
submittable     : True        ← 却说可以提交
```

**"零个参数、且一个都不缺"**——这个签名是错的，但它不报错、字段齐全、值都合理。消费方按 `not missing` 判可提交，就把一个参数根本没解析出来的链当成能跑的送去执行了。

根因：`fastqc` 的输入类型是 `Array[File]+`，而代码三处都在拿字符串**精确相等**判类型（`if type in ("File", "Array[File]")`），带 `+` 后缀的匹配不上。三处全漏，等于这张卡在执行参数解析里**完全不存在**。

修法：抽出 `_base_type()` / `_is_file_type()` / `_is_array_type()` 三个小函数，三处统一调用。

> 讲课要点：**最危险的 bug 不是崩溃，是"错得像对"。** 崩溃你立刻知道；返回一份格式完美、字段齐全、看不出异常的错误答案，可能几个月都没人发现。这也是为什么我们补测试时特意要求：**断言要落在"不能声称可提交"上，而不只是字段值**。

### 6.8 `validate_plan(plan)` — 接地校验

**干什么：** 把整份 Plan 交给它，逐条核验：
- 里面的工具在不在 51 个闭集目录里？
- 文件名在图里真的存在吗？
- 路径是图谱记录的那个吗？
- 队列号是真的吗？

**怎么调：**
```json
{"name": "validate_plan", "arguments": {"plan": { ...完整的 tool-chain/v2 JSON... }}}
```

**返回：** `grounded`（布尔）+ `violations`（违规清单）。

**什么时候用：** 输出最终答案前调一次。`grounded=false` 时按 `violations` 修正后**再验一次**。

**⚠️ 在我们的网页服务里，模型看不见这个工具。** 服务端在模型给出终答之后**自动跑**它。原因写在代码注释里：

> 这是个纯校验闸门、没有信息产出。让模型自己调它，就多花一整轮模型延迟——而且实测轨迹里它还常被连调 2-3 次。

对比一下：`validate_atomic_chain` 就**保留**给模型，因为它会返回 Knowledge Card 的 `meta_id` 和槽位名，**是个信息源**，模型拿到之后要用。

> 讲课要点：**"这个工具给模型看还是服务端自己跑"的判据是——它有没有信息产出。** 有产出的（返回模型不知道的事实）给模型；纯闸门型的（只回 yes/no）服务端代跑，省一轮。

---

### 6.9 `hydrate_plan(plan)` — 确定性补全

**干什么：** 把 Plan 里**图谱和闭集目录本来就知道的字段**由服务端填上。

**服务端会填的：**
- `tool` 块里的 `catalog_id` / `tool_kind` / `name` / `description` / `inputs` / `outputs`
- asset 的 `file_path` / `format` / `data_level` / 各种 accession
- 原子链的卡内槽位
- `match_id` / `rank` / `source` / `recommendation_count` / `candidate_count`
- `planner_metadata` / `data_matcher_mode` / `mcp_timing_ms`

**模型只需要写"判断性内容"：**
- `schema_version`、`selection_status`、`intent`
- 每条推荐的 `pipeline_id`、`match_note`（推荐理由）
- asset 的 `file_name` + `match_reason`
- candidates 链的步骤顺序

**怎么调：**
```json
{"name": "hydrate_plan", "arguments": {"plan": { ...精简版 Plan... }}}
```

**为什么要有它——这是最直接的提速手段之一：**

大模型是**逐 token 生成**的。它写 200 个字符的样板字段，就要花 200 个字符的时间。而这些字段：

1. **服务端本来就知道**（查图谱/目录即得）
2. **模型写了也会被覆盖**（以图内事实为准）
3. **模型写它反而危险**——`file_path` 这种字段，模型很容易凭记忆编一个出来

所以手册里直接写死：**这些字段一律不要生成。**

同样地，网页服务里这个工具对模型不可见，服务端在终答后自动跑。

**顺带一提**，手册里还有一条相关的紧凑输出要求：**JSON 不缩进、不美化**。缩进也是 token，也要花生成时间。

## 7. 第四层：编排层（把上面三层串起来）

`web/server.py` 是一个 **纯 Python 标准库**写的 HTTP 服务——不装任何第三方包，`python3 web/server.py` 就跑起来。默认端口 8017。

它干五件事：

### 7.1 拼系统提示词

启动时把 `web/manual_compact.md` **全文读进来，内联进系统提示词**，并附一句：

> 【手册已内联】规划手册（即 `get_planning_guide` 返回内容）全文已在下方给出，本会话**不需要**再调用 `get_planning_guide`，直接从下文手册行事。

**省掉的是"取手册"那一整轮往返。**

### 7.2 过滤模型可见工具

MCP server 端 10 个工具**一个都不删**（其他客户端要用），但对**网页会话里的模型**隐藏三个：

| 隐藏的工具 | 原因 |
|---|---|
| `get_planning_guide` | 手册已内联，零调用 |
| `validate_plan` | 纯闸门无产出，服务端终答后自动跑 |
| `hydrate_plan` | 确定性补全，服务端自动跑 |

模型实际看到 **7 个**工具。

### 7.3 跑 function-calling 循环

**function calling（函数调用）** 是现代大模型的一个能力：你告诉它"你有这些工具，各自要什么参数"，它在回答过程中可以说"我要调用 `read_cypher`，参数是这个"，你替它调完把结果喂回去，它接着想。

循环大致是：

```
1. 把系统提示词 + 用户问题发给模型
2. 模型返回：要么是最终答案，要么是"我要调这几个工具"
3. 若是工具调用 → 转发给 MCP server → 拿到结果 → 喂回模型 → 回到 2
4. 若是最终答案 → 进入 7.4
```

**两个硬限制：**
- `MAX_ROUNDS = 15` —— 工具调用轮数总上限（手册纪律要求 5-8 次以内）
- `QUERY_ROUND_BUDGET = 3` —— **取数轮数预算**，用尽后服务端会告知模型"预算已用尽"，逼它收敛出答案

第二条是我们攻 p90/p99（长尾延迟）时加的**硬闸门**。手册里的"纪律"是软约束——模型可能不遵守；这个预算是**服务端强制执行**的。

### 7.4 终答后的两步自动处理

模型给出终答之后，服务端**自动**做两件模型不知道的事：

```
终答 JSON
  → hydrate_plan（补全所有样板字段）
  → validate_plan（接地校验）
  → 推给前端
```

这两步各省一轮模型延迟。

### 7.5 SSE 推流

**SSE = Server-Sent Events**，一种服务端向浏览器持续推送数据的技术。前端（`web/index.html`，单文件、无 npm 依赖）用它实时显示：

- **思考段**——模型正在想什么（Kimi 风格的可折叠推理过程）
- **工具调用可视化**——正在调哪个工具、参数是什么、返回了什么

用户看到的不是一个转圈圈的加载图标，而是**整个推理过程**。

```json

```
但**合理的聚合需求照常服务**——"有多少样本带生存数据"是正常问题，用 `count` / `IS NOT NULL` 查。

而且就算模型没拦住，`read_cypher` 服务端守卫也会拦。**两道防线。**

## 9. Benchmark：我们怎么证明它有用

这一章值得单独讲，因为**它讲的是"怎么诚实地评估一个 AI 系统"**——这个方法论比具体数字更有价值。

### 9.1 先测污染，再谈准确率

我们接手时有一套 96 例测试集，原版在上面**拿 100%**。

第一件事不是去优化，是去**检查这套题本身**。

写了个污染度检测：用一张 78 词的关键词表，逐条去题面里找答案触发词。结果：

> **96 / 96（100%）的问题文本直接包含答案触发词。**

也就是说，题目问"请对该队列做 WGCNA 共表达网络分析"，答案就是 `wgcna`。

**在这套集子上拿 100% 不说明任何事——它是一份"答案泄漏集"。**

> 讲课要点：这是评估工作里最容易被跳过、也最值钱的一步。**先问"这套题能不能区分好坏系统"，再问"我们考了多少分"。** 一套所有人都能满分的卷子，分数是零信息量的。

### 9.2 三臂评测

光说"题泄漏了"是空口，得**量化证明**。方法：设三条对照臂，跑同一批题。

| 臂 | 是什么 | 作用 |
|---|---|---|
| **floor（地板）** | 永远猜最高频的那个工具 | 随机猜的水平，性能下界 |
| **ceiling（天花板）** | 一张 60 行的关键词对照表 | **纯规则**能做到多好——不含任何 AI |
| **SUT（被测系统）** | skill + read-cypher + 真实大模型 | 我们的系统 |

跑出来：

| 臂 | 原集 96 例 | **去名集 70 例** |
|---|---|---|
| floor | ~12.5% | **7.1%**（= 随机线） |
| ceiling（60 行关键词表） | **100%** | **1.4%** |
| SUT（严格 top-1） | — | **35.8%**（67 例样本） |

**"去名集"是什么：** 我们另建了一套 70 道题（14 个工具 × 5 例），**只写意图、不出现任何规则触发词**，并且程序化验证过与关键词表**零重叠**。

比如不说"做 WGCNA"，改说"我想找出一组表达模式相似、并且和临床分期相关的基因"。

**这张表要这么读：**

1. **ceiling 从 100% 崩到 1.4%** —— 一张 60 行关键词表在原集上满分，题面一改写就**比随机猜还差**。这就是"原集的 100% 全是词表泄漏"的**铁证**。
2. **SUT 35.8%，是 ceiling 的 25 倍** —— 在去掉关键词提示的题上，真正需要理解意图，规则彻底失效，模型还能做对三分之一。
3. **35.8% 这个绝对值不高，我们诚实报出来** —— 见 9.4 的失败分析。

> 讲课要点：**三臂设计的精髓是 ceiling 臂。** 它回答的是"不用 AI，用最笨的规则能做到多少"。如果 AI 系统跑不赢 ceiling，那 AI 就是纯粹的浪费。反过来，看到 ceiling 在去名集上崩到 1.4%，才知道这套题真正在考什么。

### 9.3 评分口径的演进（诚实记录）

最初我们报的是 **87.1%**。后来发现那是**子串匹配**——期望的工具名只要在全文任何地方出现过就算对。

问题有二：
1. `survival_analysis` 是 `tmb_survival_analysis` 的子串，永远误判为命中
2. "提到即命中"等于送分：模型写"可以考虑 A、B、C 三个流程"，只要正确答案在里面就算对

改成与 ceiling 同口径的**严格 top-1**（只解析 `recommendations[0].tool.pipeline_id`）后，掉到 **35.8%**。

三个口径并列报告：

| 口径 | 数值（67 例） | 含义 |
|---|---|---|
| 子串（旧，已弃用） | 85.1% | 软：提到即算 |
| **严格 top-1** | **35.8%** | 硬：与 ceiling 可比 |
| 格式合规率 | 52% | 模型半数写散文，没遵守输出契约 |
| 结构化子集内准确率 | 69% | **遵守契约时**的工具选择质量 |

> 讲课要点：**评分口径变了要说，掉分了也要说。** 87.1% → 35.8% 不是系统变差了，是尺子换准了。把旧口径一起列出来，读者才能判断这个变化是什么性质。

### 9.4 两个比数字更重要的发现

**发现一：生存族 0/5。**
图谱里 `km_survival` / `cox_model` / `survival_analysis` / `tmb_survival_analysis` / `her2_pfs_survival` 五个工具**意图高度重叠**。模型稳定地选到"合理但不是标准答案"的那个。

这**不是模型的错，是标注问题**——"题库单解 vs 图谱多解"。用户说"做个生存分析"，图里有五个都对。

（顺带一提，这个发现直接推动了手册 §12.1 增加"同族工具判别"一节：明确写死 `survival_analysis` 按**指定基因的突变状态**分组、`tmb_survival_analysis` 按 **TMB 中位数**分组、按**基因表达水平**分组的是 `her2_pfs_survival`。）

**发现二：输出契约只执行 52%。**
即使系统提示词里强制要求"输出单个 JSON"，模型仍有近半数写成散文。

**这个发现直接决定了架构：既然模型的格式合规率只有一半，校验层就必须存在，而且必须在服务端。** 不能指望"提示词写得够严就行"。

（也正因为这个，我们给前端的接入建议里写了**三道断言，缺一不可**：① Plan 带 `schema_version: "tool-chain/v2"`；② `validate_plan` 返回 `grounded=true`；③ 提交前 `validate_execution_chain` 返回 `submittable=true`。断言失败把错误喂回模型重试 2-3 次，仍失败就如实报错。）

### 9.5 数据面核查

除了工具选得对不对，还要看**数据选得对不对**：

- 96 例期望的文件，图内可查 **174 / 186（93.5%）**
- 其中**精确命中 138 / 186（74.2%）**，宽匹配命中 36（19.4%）
- 6 例（q052–057）期望的是 demo 文件（`NVM0598_*`、`ENCSR142YZV_chr19only_*`），**不在图里**——以图为准，如实报 `missing_from_graph`

### 9.6 24 例回归门禁（日常开发用）

三臂评测是"这个系统行不行"的评估，跑一次要很久。日常改代码需要一个**快速门禁**：24 个代表性问题，8 并行跑一遍。

**门禁标准（硬性，不达标不许推送）：**
- 通过率**不许掉**
- 平均耗时**应下降**
- 轨迹**必须落盘**（每个 case 一个 JSON，存 `web/tests/trajectories_<时间戳>/`）

**这次精简手册后的实测**（每次都是 24 例、8 并行）：

| 运行 | 通过 | mean | p50 | p90 | p99 | max | >30s |
|---|---|---|---|---|---|---|---|
| 精简前（基线） | 24/24 | 7.1s | 5.8s | 16.7s | 21.5s | 21.5s | 0 |
| 精简后 #1 | 24/24 | 7.9s | 6.9s | 17.7s | 36.5s | 36.5s | **1** |
| 精简后 #2 | 24/24 | 7.1s | 6.8s | 17.7s | 22.7s | 22.7s | 0 |
| 精简后 #3 | 24/24 | 6.9s | 5.9s | 15.2s | 17.9s | 17.9s | 0 |
| **再修正三处过时事实后 #1** | 24/24 | 8.2s | 5.2s | 18.9s | 41.5s | 41.5s | **1** |
| 再修正后 #2 | 24/24 | 7.0s | 6.1s | 15.5s | 27.3s | 27.3s | 0 |
| 再修正后 #3 | 24/24 | 6.6s | 6.4s | **13.6s** | 21.0s | 21.0s | 0 |
| **再修正后合并（n=72）** | **72/72** | 7.3s | 6.1s | **14.6s** | 27.3s | 41.5s | 1 |

**怎么读这张表（诚实版）：**

- **通过率 144/144**（精简后 72 + 修正后 72），一次没掉。
- **合并 p90 = 14.6 秒，比修正前任何一次都好**（基线 16.7、其余 15.2~17.7）。
- 平均耗时在 6.6 ~ 8.2 秒之间波动，基线 7.1 秒。**结论是"持平"，不是"下降"。**
- 这符合预期：这两轮改动加起来只动了系统提示词里约 2 KB（占比约 0.5%），**本来就不该产生可测量的加速**。收益是**准确性和可维护性**，不是速度。
- **仍有一例越过 30 秒的风险，如实报出**：q08 三次跑出 41.5 / 27.3 / 13.6 秒，方差极大。看轨迹，慢的那次走了 4 轮，且 **`validate_atomic_chain` 被调了两次**——而手册明写这个工具"组装完调**一次**"。这是模型没守纪律，不是新引入的退化（修正前那轮最慢的也是 q08，22.7 秒）。**这是当前长尾的头号目标**，见 §11.2。

> 讲课要点：**n=24 的单次测量，噪声可能大于效应。** 看到一个数字变好就宣布优化成功，是最常见的自欺。这两轮我们各跑了三遍才敢下结论，而且下的都是"持平"这个不好看的结论。

**历史优化轨迹**（这些才是真正带来提速的改动）：

| 时点 | mean | p90 | 主要改动 |
|---|---|---|---|
| 早期 | 7.8s | 18.5s | — |
| 中期 | 7.5s | 17.6s | 执行契约对齐（P0-1/2/3） |
| 近期 | 7.1s | 16.7s | 手册补 `tool_id` 说明 |
| 本次 | 7.1s | ~16.7s | 手册精简（持平） |

真正的大头提速来自更早的几轮：**手册内联**（省取手册那轮）、**`hydrate_plan` / `validate_plan` 服务端自动化**（各省一轮）、**`get_study_overview` 聚合接口**（三查合一）、**取数轮数硬预算**。这些是"从 30 秒量级降到 7 秒量级"的原因。

### 10.3 最诚实的一句话

README 里写着这么一段，值得原样念给听众：

> **本仓库的真实论点**：205MB 重 MCP → 110KB。96 例上，一张 60 行关键词表即可与重服务打平——**该任务的工具选择本身是平凡的，重架构从未在此挣到收益**。真正需要模型智能的是"去名"的意图理解。

这句话的分量在于：**它承认了"我们打平的那 96 例，本来就不难"。**

真正的价值不在"我们在 96 例上也拿了满分"，而在：
1. **用 1/1800 的体积拿到了同样的结果** —— 说明那 205 MB 里绝大部分是没有产出的
2. **建立了一套能区分好坏的评测** —— 去名集才是真考题
3. **在真考题上，规则崩到 1.4%，模型还有 35.8%** —— 这才是 AI 挣到的那部分

### 10.4 几个可以单独展开讲的工程决策

这些不是"功能"，是**方法**，讲给老师听可能比功能列表更有意思：

**① 显式白名单 > 关键词启发式。**
参考资源判定用 `(卡片 id, 参数名)` 二元组列举，正好 5 条。原因就是 `bcftools.filtered_vcf_index` 那个反例——名字带 `index` 但不是参考资源。重版按关键词判，把一条必需绑定判没了。

**② 宁可缺，不给静默覆盖的错值。**
多步链里 `trim_galore.read1` 和 `star.read1` 冲突时，扁平视图**剔除**该键并列进 `ambiguous`，而不是让后者覆盖前者。**给一条错路径比不给路径危险得多。**

**③ 按结构判定，不按名字判定。**
隐私守卫按 `01_`–`13_` 数字前缀拦，不按"字段名看着像不像临床数据"。上游新增编号列自动被拦住。

**④ 有信息产出的工具给模型，纯闸门型的服务端代跑。**
`validate_atomic_chain` 返回卡片 meta_id 和槽位名 → 给模型。
`validate_plan` 只回 yes/no → 服务端跑，省一轮。

**⑤ 能确定性算出来的，绝不让模型算。**
样本角色、文件路径、工具描述、闭集成员资格——全部是代码的活。**模型只做"判断"，不做"记忆"。**

**⑥ 测试要能失败。**
补 P0 断言时，特意**拿改动前的代码验证过每条断言都会失败**。能过的测试不等于能失败的测试——一条永远为真的断言等于没写。

## 11. 后续优化方向

分四个层次讲，从近到远。

### 11.1 近期：把已知的账还掉

**先说一个刚发生的例子，它正好说明"手册新鲜度"为什么排第一。**

写这份文档时，为了给第 4 章填节点数量表，我顺手去图里查了一遍。结果发现手册 §2 写着：

> `tissue_type` 不是干净二值：Tumor 5469、Normal 2469、null 1270、**多值 `Tumor,Normal` 700**、Blood 557

而 0821 图谱的真实分布是：

> Tumor **6258**、Normal **2821**、null **829**、Blood 557，**多值单元 0 个**

五个数字里错了三个，而且"700 个多值单元"整类已经不存在了——0821 交付把它们清干净了。手册还据此告诉模型"HRA016026 的 700 个样本全是 `Tumor,Normal`"，实际上那个队列现在是干干净净的 350 `Tumor` + 350 `Normal`。

**最讽刺的是：同一个文件的 §12.4 里写着"`tissue_type` 本身有 829 个样本为空"——和实测一致。** 也就是说 §12.4 更新过，§2 没有，**同一份手册里两节自相矛盾了不知道多久，没人发现**。

（已修正，两份手册同步，并重跑了三遍 24 例回归确认通过率没掉。这类错不会让查询报错，只会让模型带着错误的前提去写 Cypher。）

| 项 | 现状 | 建议 |
|---|---|---|
| **手册新鲜度检查** | 图谱换版本后 §12 快照必须重新推导，目前**靠人记得**——上面就是漏网的例子 | 写个 `check_manual_freshness.py`：把手册里的实测数字逐条去图里复查，对不上就报警。**这个投入产出比最高，建议优先做** |
| `integration_test.py` 7 个失败 | 全是 0821 数据问题（字符串型数值、format 大小写孤儿、`00_sample_accession` 与边错位 349 个），其中 5 条是修完崩溃点后才首次暴露 | 逐条与图谱交付方对齐；有些要上游修数据，不是代码能解决的 |
| `io_slot.csv` 的 `required` 反了 | gatk 四个 paired BAM/BAI 槽在槽表里是 `required=false`，Knowledge Card 里是 `true`；`interval_list` 正好相反 | 不影响生产（light 走卡片不走槽表），但文件随 skill 分发，建议上游查一下 WDL 重建时是不是漏了回填 |
| `light_router.load_slots()` 先天缺陷 | 键只有 `(tool_id, slot_name)` **不含 direction**，同名的输入/输出行会撞，输出赢（同步前 19 处冲突，同步后 17 处） | 它在**已下线的离线对照臂**里，按交接文档 §5 明确不动。记录在案即可 |
| **q08 长尾** | 三次跑出 41.5 / 27.3 / 13.6 秒，慢的那次走 4 轮且 `validate_atomic_chain` 被调两次（手册要求只调一次） | 当前**唯一还会破 30 秒的用例**。先看轨迹确认是不是"链改了所以重验"，是的话在手册里补一条"改链后允许复验一次，但必须与其他查询同轮发" |
| `QUERY_ROUND_BUDGET` 调参 | 代码默认 3，没做过 A/B | 试试 2。可能进一步压 p90，也可能掉通过率——**必须用 24 例门禁验，不能拍脑袋** |

### 11.2 中期：评测与质量

**① 把去名集扩大。**
现在 70 例（14 工具 × 5）。图里有 51 个工具，覆盖不到三成。扩到全覆盖才能看清哪些工具族是真的分不开。

**② 解决"题库单解 vs 图谱多解"。**
生存族 0/5 那个发现说明标注方式有问题。两条路：
- **改评分**：允许一题多个可接受答案（用图谱的 `has_function` 关系自动生成等价类）
- **改图谱**：给同族工具补充判别性描述，让它们真的能被区分开
（后者我们已经在 §12.1 做了一轮，可以量化验证一下有没有效）

**③ 攻格式合规率。**
52% 太低。可以试：
- 更强的结构化输出约束（但**注意**：我们的"不要重复"清单里明确写着 —— **`response_format: json_object` 试过了、单纯在提示词里加输出格式约束试过了，都不work**）
- 服务端做一层"散文 → JSON"的抢救性解析（现在已经有 `stripped_prose_or_fence` 的兜底，可以看看它救回来多少）

**④ 长尾治理。**
p99 目前 18-23 秒。看轨迹，慢的 case 普遍是**多轮取数**。可以针对性地：找出哪些问题类型稳定要 3 轮以上，看看能不能像 `get_study_overview` 那样再焊一个聚合接口出来。

### 11.3 远期（重点）：从"调图谱"到"调所有生信工具"

**这是最值得展开讲的一节，也是这个架构真正的扩展方向。**

#### 现状的边界在哪

现在整个系统被**闭集**框住了：51 个工具（11 个可编排原子 + 38 个 pipeline + 1 个 task_pipeline）。这 51 个都在图谱里，都有格式契约，都有 `next_tool` 边。

好处是**绝对可靠**——不在闭集里的一律不许出现，杜绝了幻觉。

代价是**天花板很低**。用户问"我想做 ATAC-seq 分析"、"我想用 Seurat 做单细胞聚类"、"能不能跑个 nf-core 的 RNA-seq 流程"——系统只能回 `unsupported`。

而真实的生信生态有多大？

- **Bioconda** 上有 **9,000+** 个生信软件包
- **nf-core** 有 **100+** 条经过社区验证的标准流程
- **Galaxy ToolShed** 有 **8,000+** 个工具
- **Bioconductor** 有 **2,300+** 个 R 包
- 还有 **WorkflowHub**、**Dockstore**、**bio.tools**（约 **30,000** 条工具注册记录）

**我们现在覆盖了其中的 51 个。**

#### 三条可能的路径

**路径 A：扩闭集（保守，工程量线性增长）**

继续现在的做法：每接一个新工具，就写一张 Knowledge Card、在图里加节点和 `next_tool` 边、更新 `tool_catalog.csv`。

- **优点**：可靠性完全不变，架构一个字不用改
- **缺点**：**不可扩展**。51 → 500 意味着 500 张手写卡片。而且 `next_tool` 边是 O(n²) 的——工具越多，人工维护关系越不现实
- **适用**：核心的、高频的、必须绝对可靠的工具

**路径 B：分层可信度（推荐，这是我认为最实际的方向）**

不再是"闭集内 / 闭集外"的二元判断，改成**三层**：

```
┌──────────────────────────────────────────────────────────┐
│ L1  核心闭集（现在的 51 个）                                │
│     有 Knowledge Card、有图谱边、有格式契约                  │
│     → 可以进 candidates[]，可以做执行参数解析                │
│     → submittable 可以为 true                             │
├──────────────────────────────────────────────────────────┤
│ L2  已注册工具（从 bio.tools / Bioconda 元数据自动导入）      │
│     有名字、有描述、有输入输出格式声明，但没人工核过           │
│     → 可以进 recommendations[]，但标记 tier: "registered"  │
│     → submittable 一律 false，必须人工确认                 │
├──────────────────────────────────────────────────────────┤
│ L3  模型建议（模型从自身知识提出，图谱完全不知道）             │
│     → 只能进一个新字段 suggestions[]，明确标注"未经核实"      │
│     → 绝不进 recommendations[]，绝不给路径                 │
└──────────────────────────────────────────────────────────┘
```

**关键在于：接地纪律不放松，只是变得分层。**

现在的规则是"不在闭集里就不许提"。改成"不在闭集里**可以提，但必须带着可信度标签，且不许给出执行参数**"。

这样：
- 用户问 ATAC-seq，系统可以说"图谱里没有现成流程，但 bio.tools 注册了 MACS2 / Genrich，这是 L2 建议，需要你自己确认可用性"
- 而不是干巴巴一句 `unsupported`
- 同时**绝不会**把一个没核过的工具当成能跑的方案送去执行

**工程量估计**：需要一个 bio.tools / Bioconda 元数据的导入器（它们都有开放 API 和结构化元数据），一个新的 `tier` 字段，Plan 契约升到 v3，手册加一节分层规则。**架构不用推翻。**

**路径 C：自动构建 Knowledge Card（激进，但可能是终局）**

现在的 Knowledge Card 是人写的 YAML，声明工具的输入输出参数、类型、必需性。

但注意一件事：**重版 0823 那轮，槽表是从 WDL 文件重建的**（commit `58f6be6`，246 行 19 列）。

**WDL（Workflow Description Language）是机器可读的**——`task` 定义里明明白白写着每个参数的名字、类型（`File` / `Array[File]+` / `File?` / `String`）、是否可选。这些信息**本来就可以自动提取**。

同样的道理适用于：
- **nf-core** 流程的 `nextflow_schema.json`（严格的 JSON Schema）
- **Galaxy** 工具的 XML 定义（`<inputs>` / `<outputs>` 结构化）
- **CWL** 的 `CommandLineTool` 定义
- **Snakemake** 的 rule 定义（半结构化）

**设想的自动化管线：**

```
WDL / nextflow_schema.json / Galaxy XML / CWL
        ↓ 解析器（每种格式一个，都是确定性代码）
   Knowledge Card（自动生成）
        ↓ 格式契约推断
   图谱节点 + input/output 边
        ↓ 格式匹配（A 的 output 格式 = B 的 input 格式）
   next_tool 边（自动推导！）
```

**最后一步是关键**：`next_tool` 关系现在是人工维护的，但它本质上就是"**上游输出格式 ∩ 下游输入格式 ≠ ∅**"。如果两边的格式声明都是自动提取的，这条边就能自动算出来。

**这一步跨过去，工具数量的天花板就从"人能写多少张卡"变成"社区发布了多少条 WDL/CWL/nf-core 流程"。**

**风险要说清楚：**
- 自动提取的契约质量参差不齐（有些工具的参数描述写得很烂）
- 格式命名不统一（一个人叫 `fastq`，另一个叫 `FASTQ_GZ`，第三个叫 `reads`）—— **需要一层格式本体映射**，这本身是个不小的工程
- 自动推导的 `next_tool` 边会有假阳性（格式对得上不代表生物学上该这么接）

**所以务实的做法是：自动提取 → 进 L2（已注册层）→ 人工审核后升 L1。** 路径 B 和 C 是配套的，不是二选一。

#### 顺带能解决的两个老问题

**① 图谱构建自动化。**
现在图谱是从 31 个 CSV 用 `load_graph.cypher` 灌进去的，CSV 由上游手工产出。如果格式契约能自动提取，工具子图（tool / function / format / next_tool）就能自动生成，人只需要维护数据子图（study / sample / T1 / T2）。

**② 版本漂移。**
现在 `skill/references/` 下的三个文件是上游的**快照**，会漂移——这次就为了同步 `io_slot.csv` 折腾了一轮（还一度找错了目录，把一个未版本化的 pre-0823 副本当成了真值）。如果契约能自动从上游源文件重新生成，**漂移问题在源头消失**。

### 11.4 更远：跳出"规划"这个边界

现在系统只出方案，不跑分析。往下走有几个方向：

**① 接执行端闭环。**
`validate_execution_chain` 已经能算出可以直接下发的 `execution_params`。差的只是"投递 + 追踪"。接上 Cromwell（WDL 执行引擎）或 Nextflow，就能从"这是方案"变成"已经在跑了，进度 30%"。

**② 结果回灌图谱。**
分析跑完产出新的 T2 文件。如果能自动回灌进图谱，图就会**自己长大**——下次别人问同类问题，系统能说"这个分析已经有人跑过了，结果在这，直接复用"。
**注意手册里已经有"复用"这条纪律了**（"T2 有现成 VCF/MAF/BAM 就标复用、跳过上游"），只是现在的 T2 是静态的。

**③ 多轮交互式规划。**
现在是一问一答。真实场景里用户常常是"先看看有哪些数据 → 哦这个队列不错 → 那用它做个差异表达 → 再加个富集"。需要跨轮次的上下文管理和方案增量修改。

**④ 方案对比。**
同一个需求给 2-3 个方案，标注各自的数据要求、预期产出、计算量，让用户选。现在是严格 top-1，**有意为之**（为了和 ceiling 臂可比），但对真实用户未必是最优交互。

## 12. 名词速查表

| 名词 | 解释 |
|---|---|
| **MCP** | Model Context Protocol，模型调用外部工具的开放标准。相当于 AI 工具界的 USB |
| **Skill** | 写给 AI 看的操作手册。纯文本，被读进模型上下文作为行动指南，不是代码 |
| **Neo4j** | 图数据库。用节点和关系存数据，而不是表格 |
| **Cypher** | Neo4j 的查询语言，相当于图数据库的 SQL |
| **知识图谱** | 用"点 + 线"表示实体和实体间关系的数据组织方式 |
| **接地 / grounding** | 答案里每个具体名词都能追溯到真实来源，不是模型编的 |
| **幻觉 / hallucination** | 大模型编造看起来合理但实际不存在的内容。**置信度和说真话时完全一样** |
| **闭集 / closed set** | 允许出现的工具是一个固定的、有限的集合，多一个都不行 |
| **atomic tool** | 单个生信软件（bwa / gatk / star），可以串成链 |
| **pipeline** | 打包好的完整业务流程（diff_expr_go），不参与串链 |
| **Knowledge Card** | 描述一个原子工具接口契约的结构化文件：参数名、类型、是否必需、格式 |
| **Plan / tool-chain/v2** | 系统的输出契约，一份结构化 JSON，描述完整分析方案 |
| **round / 轮** | 一次完整的模型推理。**是本系统唯一的时间成本**（几秒~几十秒） |
| **function calling** | 大模型主动请求调用外部工具的能力 |
| **SSE** | Server-Sent Events，服务端持续向浏览器推送数据 |
| **T1 / T2** | 图谱里的两类文件节点。**T1 = 原始 FASTQ，T2 = 一切加工产物**（BAM/VCF/MAF/矩阵） |
| **HRA****** | 队列（study）编号，如 HRA001272 = 肝癌队列，698 样本 |
| **HRR****** | run 编号，出现在文件名里 |
| **MAF** | Mutation Annotation Format，突变注释格式。**全图只有 7 个队列有** |
| **TPM / FPKM / counts** | 表达矩阵的三种定量口径。同一个队列三份都有，图属性完全相同，**只有文件名能区分** |
| **tumor / normal 角色** | 样本是肿瘤还是正常对照。**必须用 `resolve_sample_roles` 判，不许猜** |
| **去名集** | 去掉了所有规则触发词的测试集，只写意图。**用来暴露关键词表的虚假高分** |
| **三臂评测** | floor（随机）/ ceiling（纯规则）/ SUT（被测系统）三条对照臂 |
| **严格 top-1** | 只看第一推荐是否命中的评分口径，与 ceiling 可比 |
| **p90 / p99** | 百分位延迟。p90 = 90% 的请求在这个时间内完成。**长尾优化的核心指标** |
| **WDL / CWL / Nextflow** | 三种工作流描述语言，都是机器可读的。**这是自动化扩展的入口** |

## 附：讲课时可以重点展开的几个故事

如果时间有限，这几个故事比功能列表更能说明问题：

1. **"96/96 题面泄漏"** —— 先验题，再考试。一套所有人都满分的卷子，分数是零信息量的。（§9.1）
2. **"ceiling 从 100% 崩到 1.4%"** —— 怎么用一个对照臂，把"虚假的满分"证明成虚假的。（§9.2）
3. **"零个参数、且一个都不缺，却说可以提交"** —— 最危险的 bug 不是崩溃，是**错得像对**。（§6.7）
4. **"名字带 index 但不是索引"** —— `bcftools.filtered_vcf_index` 的反例，为什么显式列举永远赢过关键词猜。（§6.7）
5. **"测试崩在第 109 行，后面十几条断言从来没跑到过"** —— 绿色的 CI 可能只是意味着它提前停了。（§9.7）
6. **"1470 个正常血样被标成原发肿瘤"** —— 脏数据的可怕之处在于它**看着完全正常**。（§4.3）
7. **"87.1% 改成 35.8%"** —— 换准了尺子，分数变难看，但可信了。（§9.3）
8. **"跑了三遍才敢说'持平'"** —— n=24 的单次测量，噪声可能大于效应。（§9.6）
9. **"同一份手册里，§2 和 §12.4 自相矛盾了不知道多久"** —— 写这份文档时顺手查图，才发现手册说 `tissue_type` 有 700 个多值单元、而 0821 图里一个都没有。**文档本身成了一次审计。**（§11.1）
